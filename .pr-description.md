# QOS-25: Process uploaded MP4 media with bounded jobs and retry-safe output

Linear issue: https://linear.app/qosapp/issue/QOS-25/process-uploaded-mp4-media-with-bounded-jobs-and-retry-safe-output

## Summary

This PR implements asynchronous video processing for product MP4 uploads with bounded resource usage, retry-safe idempotency, and inspectable failure handling. The implementation extends the existing media storage and authorization infrastructure (from QOS-98) to support video content.

## Outcome

Validated product MP4 is processed asynchronously into approved playback + poster assets without blocking web requests or exhausting shared resources.

## Implementation

### 1. Video Processing Configuration (`src/lib/media/video-config.ts`)

- **OWNER-LOCKED LIMITS (approved for production):**
  - Max file size: **20 MiB** (20 * 1024 * 1024 = 20,971,520 bytes)
  - Max duration: **25 seconds**
  - Max resolution: **1920x1080** (Full HD)
  - Allowed codecs: **h264, h265** (HEVC)
  - Allowed containers: **mp4, mov**
  
  **⚠️ These limits are owner-approved and must not be changed without explicit owner authorization.**
  
- **Configurable via environment variables (for testing/overrides only):**
  - `VIDEO_MAX_UPLOAD_BYTES` (default: 20 MiB)
  - `VIDEO_MAX_DURATION_SECONDS` (default: 25s)
  - `VIDEO_MAX_WIDTH` / `VIDEO_MAX_HEIGHT` (default: 1920x1080)
  - `VIDEO_ALLOWED_CODECS` (default: h264,h265)
  - `VIDEO_ALLOWED_CONTAINERS` (default: mp4,mov)
  - `VIDEO_MAX_CONCURRENT_JOBS` (default: 2)
  - `VIDEO_MAX_RETRIES` (default: 3)
  - `VIDEO_JOB_TIMEOUT_MS` (default: 5 minutes)

### 2. Bounded Validation (`src/lib/media/video-validation.ts`)

- Uses `ffprobe` to validate video metadata before processing
- Enforces all configured limits BEFORE decode/transcode
- Rejects mislabeled, over-limit, or corrupt files with clear error messages
- No unbounded worker operations or hung upload requests

### 3. Database Schema (`drizzle/0034_eager_monster_badoon.sql`)

Extended media schema to support video processing:

- **New enum values for `media_derivative_kind`:**
  - `video_playback` - transcoded video suitable for web playback
  - `video_poster` - extracted poster frame (JPEG)

- **New table `video_processing_jobs`:**
  - Tracks tenant/product/asset identity
  - Maintains job status: `queued`, `processing`, `ready`, `failed`, `rejected`, `quarantined`
  - Records retry count and last error message
  - Unique correlation ID for inspectability

### 4. Durable Job Queue (`src/lib/media/video-job-queue.ts`)

- **Queueing:** Creates durable work items with tenant/product/source-version identity
- **Processing:** Claims jobs optimistically, processes with bounded resources
- **Idempotency:** Replays do not leak files or double-count quota
  - Existing derivatives are deleted before creating new ones
  - Exactly one approved derivative/poster set per logical source job
- **Retry handling:**
  - Automatically retries failed jobs up to configured maximum (default: 3)
  - Increments retry count on each failure
  - Moves to `quarantined` state after exhausted retries
- **Failure visibility:** Records last error message and timestamp with correlation ID

### 5. Video Transcoding (`src/lib/media/video-validation.ts`)

- Uses `ffmpeg` with bounded settings:
  - Target codec: `libx264`
  - Max bitrate: `2M`
  - Fast preset for reasonable processing time
  - FastStart flag for web streaming
- Generates poster frame at 50% of video duration
- Task-scoped: no arbitrary user command execution, no external fetch

### 6. Product Video APIs (`src/lib/media/product-videos.ts`)

Follows the existing product-images pattern:

1. **Create upload grant:** `createProductVideoUploadGrant`
   - Validates byte size and content type
   - Returns grant token and upload path
   
2. **Ingest upload:** `ingestProductVideoUpload`
   - Validates uploaded bytes match grant
   - Stores in private blob storage
   - Marks asset as `uploaded`
   
3. **Queue processing:** `queueProductVideoProcessing`
   - Creates durable processing job
   - Returns correlation ID for status tracking
   
4. **Get job status:** `getProductVideoJobStatus`
   - Returns current status, retry count, error messages
   
5. **Get approved URLs:** `getApprovedProductVideoUrls`
   - Returns public playback and poster URLs after successful processing

### 7. Authorization and Tenant Context

- Reuses existing tenant media authorization from QOS-98
- All operations require active staff membership
- Assets are scoped to tenant and product
- No cross-tenant access or foreign-tenant asset ID acceptance

## Former Operational Blockers (resolved)

The three blockers originally listed here are implemented; see README "Product video worker".

1. **Worker process:** `scripts/video-worker.ts` + `src/lib/media/video-worker.ts`. Bounded concurrency, Postgres-backed queue (no extra broker), claims via the `SECURITY DEFINER` function `qos.claim_next_video_processing_job` (migration 0035) so it runs as `qos_app`. Worker death is recovered by a claim lease; SIGTERM drains in-flight jobs.
2. **ffmpeg in production:** Dockerfile target `worker` (Node 22 alpine + ffmpeg with libx264/aac); deploy with `deploy/deploy-video-worker.cmd` to `ca-qos-dev-video-worker`. CI installs ffmpeg so the processing tests actually run.
3. **Per-tenant fairness:** least-recently-served tenant first, capped at `VIDEO_MAX_ACTIVE_JOBS_PER_TENANT` active jobs per tenant; claims are serialized so the cap is strict.
