# QOS — Vendor-neutral AI foundation and controlled migration

You are the lead engineer working in the existing QOS repository. This is an architecture review followed by an incremental refactor, not a greenfield rebuild or a new AI feature project.

## 1. Objective and first-pass boundary

QOS must be maintainable, reliable and scalable without requiring tenants or operators to configure several agent platforms. QOS owns business capabilities, security, run lifecycle, approvals, records and configuration. External AI services are replaceable implementations.

The default installation should need one AI provider account/configuration, initially OpenAI for the capabilities already in use and the proposed native Menu Manager. Hyperagent must become optional, not a mandatory dependency of core QOS.

FIRST PASS: inspect the repository and return an architecture assessment, proposed ADR-AI-02, and a file-level implementation plan. Do not change files, install dependencies, run migrations, modify Linear, invoke paid agents/models, deploy, or change provider configuration yet. Stop for owner approval after this assessment.

After approval, implement the agreed slices in reviewable PRs. Never merge or deploy without the owner's instruction.

## 2. Establish the actual baseline

Read repository instructions, the current working-tree state, and current main. Record the commit assessed. Do not reset, stash, overwrite, or switch away from uncommitted work. Identify any required baseline synchronization before implementation.

Read the available Linear items and documents:
- QOS-129: agent-platform workstream.
- QOS-132: architecture foundation.
- QOS-133: QOS MCP.
- QOS-134: Hyperagent integration.
- QOS-139 and QOS-140: existing Menu Manager and image-generation implementation.
- QOS-28 and QOS-33: spending controls and generated-media approval.
- ADR-AI-01, ADR-SF-01, the Menu Manager fast-track handoff, and repository execution conventions.

These documents contain historical assumptions. Identify conflicts; do not blindly implement them. In particular, do not reintroduce tenant-admin control of a platform provider connection, mandatory Hyperagent, duplicate audit tables, or down migrations contrary to the repository convention.

Inspect actual menu assessment, image generation, provider clients, authentication, location authorization, RLS, jobs, polling, audit, secret handling and deployment configuration. Distinguish implemented, tested, deployed, and merely described. A Done ticket does not prove every broader foundation requirement exists.

Produce an evidence-backed reuse/gap map with file paths and relevant symbols. If a source is inaccessible, identify it rather than guessing.

## 3. Target architecture: small modules, not another platform product

Use the existing application and deployment architecture. Prefer a modular monolith with an independently runnable background-worker entry point where needed, sharing application services and contracts.

Conceptual boundaries:

QOS UI / authenticated APIs
  -> QOS application services
     -> deterministic menu/catalogue/media operations
     -> QOS AI run service and durable jobs
        -> native agent executor or optional external executor
        -> model and image-provider adapters

Agent tool calls
  -> QOS tool execution boundary
  -> existing authorized application services

Optional external clients
  -> QOS MCP adapter
  -> the same QOS tool execution boundary

Do not introduce microservices per agent, databases per tenant, Kubernetes, Kafka, Redis, a workflow-design product, a vector database, or another orchestration SaaS for this work. Propose additional infrastructure only against a demonstrated requirement and obtain approval.

Preserve ADR-SF-01 storefront deployment isolation. AI work must not change storefront routing, deployments or release ownership.

Do not abstract every Azure SDK or rewrite the existing persistence layer in the name of vendor independence. Prioritize AI replacement boundaries and operational reliability.

## 4. Separate business tools, model providers and execution

Keep deterministic operations deterministic. Missing-photo counts, translation approval/staleness, price validation and modifier feasibility belong to QOS code.

Do not invoke an agent to execute a known image-generation request. That path remains:

QOS image-candidate service -> image provider -> existing media pipeline.

Use an agent only where planning or iterative tool selection adds value.

Define the smallest typed contracts required by current behavior. Reuse existing abstractions rather than creating competing versions. Suggested responsibilities, not mandatory names:
- Model inference: bounded text/structured responses and supported tool-call behavior.
- Image generation: generated bytes or constrained asset references plus provenance and usage metadata.
- Agent execution: execute or continue an agent task and report normalized results/events.
- QOS run service: authoritative persistence, scheduling, authorization, status, cancellation, retries and budgets.

SDK-specific types, thread IDs and serialized continuation objects stay inside adapters/private persistence. Menu UI and business services must not import provider SDKs.

Do not create a giant AIProvider with arbitrary method strings, any-typed payloads, or every hypothetical capability. Add import-boundary checks and reusable adapter contract tests.

Separate model selection from orchestration-framework selection. A model-provider change should not inherently require a new agent framework.

## 5. One supported default, explicit provider limitations

Target a native QOS Menu Manager using the initial OpenAI configuration. Assess the official OpenAI Agents SDK for TypeScript as an implementation dependency behind the execution adapter, not as a new hosted control plane. Reuse a suitable existing implementation if it is demonstrably simpler. Recommend one approach; do not install multiple competing agent frameworks.

Retain the current Hyperagent adapter during migration. Do not delete working behavior before replacement acceptance. Afterwards it may remain disabled for optional externally hosted tasks. Do not invent a low-level Hyperagent browser-session API that has not been verified.

Declare supported capabilities explicitly: structured output, tool calls, cancellation, continuation, usage reporting and external execution may differ. Unsupported capabilities must fail clearly or use an explicitly approved fallback, never silently weaken behavior.

Resolve and persist provider/model configuration, agent-definition version, tool-schema versions and policy version when a run starts. Configuration changes apply to new runs, not halfway through existing ones.

Provider switching means a bounded adapter/configuration change plus compatibility evaluation and rollout. It does not mean every provider supports identical behavior or that opaque in-flight state is portable.

Do not automatically switch providers after an ambiguous timeout on paid or mutating work. Drain or explicitly terminate/reconcile existing runs before retiring an adapter.

## 6. QOS owns agent definitions and business history

Keep the canonical Menu Manager definition versioned in QOS source: stable key, instructions, allowed tool names, output schema and execution limits. Use the existing configuration style; do not build an agent-authoring UI.

Tenant overrides, if required, are bounded business preferences. They must not grant tools, credentials or permissions.

Persist QOS-owned findings, execution records, tool outcomes and artifact references. Provider conversations and traces are diagnostic references, not the only copy of business results. Store accepted media in the existing QOS-owned storage workflow.

Do not introduce long-term agent memory until a concrete requirement exists. Any conversation/history store must be tenant-scoped, access-controlled and covered by retention/deletion policy. Provider-specific checkpoints must be versioned and isolated from canonical business records.

For an external provider without configuration APIs, document the manual limitation. Do not build unsupported provisioning or browser automation to work around its dashboard. No per-tenant manual provider setup is acceptable for the default product.

## 7. One authorized tool execution boundary

Define tools around existing QOS application services. Initial examples:
- menu.get_health
- menu.get_items
- catalogue.get_product
- media.create_image_candidate
- media.get_generation_status

Refine names and granularity against the code. Do not expose tools simply because a corresponding table exists.

Each tool needs a versioned input/output contract, resource-authorization rule, risk class, bounds, timeout, audit behavior and idempotency policy where relevant. Distinguish read-only, chargeable draft generation, draft mutation and protected business effects.

All agent tool execution passes through the same boundary for authorization, input validation, budget checks, service invocation, output validation and audit. Native function tools and MCP must not implement separate business rules or different security policies.

Trusted ExecutionContext is supplied by QOS orchestration/authentication, outside model-visible arguments. Model-provided product IDs are selectors that still require authorization; they are not grants.

Use the existing image-generation, quarantine, derivative, candidate-review and attachment services. Do not create a second image pipeline, bypass limits, or let an agent directly overwrite approved media.

Agents may prepare candidates and proposals. Human acceptance and publishing remain separate QOS operations. Do not expose publish, pricing changes, deletion, refunds, credentials, arbitrary SQL, unrestricted HTTP, or shell tools to Menu Manager.

## 8. Tenant isolation is enforced outside the model

Preserve verified sessions, active memberships, location restrictions, tenant-scoped transactions, composite constraints and RLS. Route tenant IDs may select a tenant only after membership/resource authorization; do not unnecessarily redesign existing routes.

Recheck current authorization at relevant tool execution and result access. Background work must carry a persisted, authorized initiating context; scheduled work needs an explicitly scoped service identity. Suspending a tenant or revoking access must prevent new protected effects.

Prevent cross-tenant leakage through caches, logs, conversations, artifacts, provider references and status endpoints as well as database queries. Never share mutable tenant context in a process-wide variable.

Test RLS using the actual restricted runtime role. Inspect worker privileges separately: do not solve queue claiming by granting a worker unrestricted access to every tenant's business data.

Do not treat prompts, public IDs, shared-workspace instructions or model-visible run tokens as hard security boundaries. A run ID is correlation, not authorization. Never put reusable bearer credentials in prompts or tool arguments to compensate for missing transport authentication.

A shared external workspace can leak through memory/history even when QOS database access is correct. Do not broaden sensitive multi-tenant external use until its isolation is demonstrated. Preserve existing behavior only within its explicitly approved scope; flag unsafe access rather than expanding it.

Native Menu Manager must not depend on solving an external provider's tenancy limitations.

## 9. Durable work and safe retries

Browser polling is a presentation mechanism, not the execution engine. Closing a tab or restarting an API replica must not lose accepted work or leave it permanently stuck.

Assess the existing Postgres lease/worker patterns first. Prefer a bounded Postgres-backed queue and worker in the current environment if adequate. Keep AI and video workloads from starving each other. Do not assume the video worker is already a general-purpose queue.

Persist an accepted job and required business state atomically. Use an outbox only where a separate event/broker publication requires it; do not add redundant queue layers.

Specify leases, heartbeat/recovery, conditional state transitions, stale-worker protection, attempt limits, deadlines, tenant fairness and global/provider concurrency limits. Keep external network calls outside long-running database transactions and locks.

Use at-least-once processing with idempotent QOS effects. Scope idempotency to tenant and operation; reject reuse of a key with different input. A repeated model call must not create a duplicate candidate or duplicate attachment.

Handle the crash window after a provider accepted a request but before QOS saved its ID. Use supported provider idempotency/reconciliation; otherwise record an uncertain outcome and block automatic resubmission until a safe resolution. Do not claim exactly-once external execution or guaranteed absence of duplicate billing.

Retry only classified transient failures, with bounded backoff/jitter and one retry owner. Account for SDK retries to prevent multiplication. Handle authentication failure, rate limiting, invalid output, refusal, timeout and unknown outcome distinctly.

Define cancellation honestly: QOS can prevent subsequent tool actions, but a provider may continue an accepted request or charge for it. Late callbacks/results must not revive terminal work or apply rejected effects.

Choose and justify the minimal run/job states. Support per-item progress for image batches so successful items survive partial failure.

Verify worker activation. Do not configure a database-polling worker to scale to zero without a tested wake-up mechanism. Propose the simplest operational option and disclose its cost.

## 10. Approvals, data validation and media safety

Use the existing review flow instead of building a generic approvals engine. Any new approval must bind to the exact tenant, resource, proposed change and source revision. Recheck permission and revision before applying; reject stale approvals and replayed commits.

Validate tool arguments and model output using the existing approved schema library. Bound collection sizes, string lengths, tokens and media sizes. Reject unknown/out-of-scope identifiers and unexpected action payloads. Schema-valid output still requires authorization and business validation.

Treat catalogue descriptions, uploaded documents, model output and tool results as untrusted content, never permission-changing instructions. Render findings safely without executing HTML or scripts.

For remotely fetched assets, enforce server-side URL/redirect restrictions, private-network protection, size/type limits and the existing quarantine pipeline. Never fetch arbitrary model-supplied URLs with platform credentials.

Retain generated-media provenance and explicit acceptance. Do not present invented ingredients, allergens or factual product attributes as verified merchant data.

## 11. Secrets, usage and observability

Provider configuration is operator-owned. Tenants see QOS capabilities, status and entitlements, not global credentials, arbitrary agent IDs or a provider-configuration maze. Disabling a tenant capability must not disable another tenant.

Disabled optional providers must not require credentials or break application startup. When AI is unavailable, normal menus, media uploads, publishing and checkout must remain usable.

Reuse Key Vault and managed identities where applicable. Properly encrypted database storage for rotating OAuth credentials can remain a valid design; assess access control, key IDs/rotation, authenticated encryption, nonce handling, refresh concurrency, backup/restore and deletion. Do not require migrating every credential into Key Vault merely to call the system production-ready.

Never put secrets in browser bundles, prompts, logs, audit payloads, container build arguments or diagnostic endpoints. Keep platform credential access distinct from tenant data access.

Enforce per-run, per-tenant and platform limits with transactional reservations before chargeable dispatch. Include maximum tool/model turns, image count, output size, runtime and concurrent work. Reconcile reservations to measured usage where available; unknown cost is not zero. Failed runs may still incur cost. Do not promise an exact hard currency cap where the provider cannot support reliable cost bounds; use conservative unit limits or refuse the operation.

Use existing observability, with QOS-owned run/correlation IDs, attempts, provider/model versions, queue age, latency, failures and usage. Do not export sensitive prompts/tool results through SDK tracing by default. External trace export requires an explicit data policy and redaction.

Define retention and tenant-offboarding behavior for results, raw responses, artifacts, audit and any provider-held data. Identify external deletion limitations rather than claiming complete erasure.

## 12. QOS MCP follows the internal foundation

Keep QOS-133, but make it a thin external adapter over the authorized QOS tool boundary. Native QOS agents should call internal tools directly; do not force internal network round trips through MCP.

After the internal path is proven, implement only a small read-only Menu Manager MCP surface first. Add draft-generation tools later with the same authorization, cost and idempotency checks.

Verify the current stable MCP specification, compatible SDK and each client's supported authentication. Use maintained libraries; do not hand-roll OAuth or cryptography.

Specify HTTPS/transport, token issuer/audience/expiry, consent, resource scopes, registration approach and revocation. Authenticate every request and authorize every resource. MCP session IDs are not authentication. Do not pass one provider's token through to an unrelated downstream service.

A shared platform OAuth connection is not blanket access to all tenants. Require a defensible tenant-bound principal or validated delegation model that does not rely on secrets exposed to the model. If a client cannot support it, restrict or defer that integration rather than weaken QOS.

Do not deploy a public MCP endpoint, create DNS or add infrastructure in the assessment pass. External MCP must not block core Menu Manager portability.

## 13. Migration sequence and proof

Propose small slices in this order, adjusting only where repository evidence justifies it:

A. Baseline assessment and proposed ADR-AI-02; no product changes.
B. Wrap existing provider calls, centralize tool policy/contracts and version Menu Manager configuration; preserve current behavior and UI.
C. Close durability, authorization, cost and observability gaps needed for reliable execution.
D. Add/prove the native Menu Manager against the same services and media pipeline, then make it the approved default. Preserve Hyperagent only as an optional adapter.
E. Add the thin, secure QOS MCP adapter and one explicitly approved external-client integration.

Use feature flags and backward-compatible forward migrations. Preserve existing runs and references. Define which in-flight runs drain on their original adapter and which require explicit cancellation/reconciliation.

For each slice specify changed files, reuse, schema/config changes, tests, rollout, rollback and acceptance evidence. Application rollback must not require destructive down migrations.

The critical acceptance test: with Hyperagent disabled and no Hyperagent credentials, QOS Menu Manager and reviewed image generation work using the single default AI-provider setup. This is the end-state test, not a claim about today's implementation.

Also test:
- Restricted-role RLS and cross-tenant/location denial across runs, artifacts, tools and caches.
- Revocation/suspension during a run and stale approval/source revisions.
- Multiple workers, lease loss, restart, duplicate requests and partial image failure.
- Ambiguous provider submission, timeout, rate limit, cancellation and late results.
- Invalid/oversized output, unknown IDs, prompt injection, unsafe URLs and secret redaction.
- Budget races, bounded retries and fair access during a busy tenant's workload.
- AI disabled/provider outage without ordinary QOS regressions.
- Provider SDK import isolation and adapter contract compatibility.
- A representative Menu Manager evaluation set measuring correctness, tool behavior, safety, latency and usage; not identical prose or pixels.

Use fakes for automated tests. Prove boundaries with an alternative fake adapter, but do not call that proof of real-provider equivalence. Use owner-approved real-provider smoke tests and documented limitations for actual portability evidence.

Propose measurable workload assumptions and reliability/latency targets for approval. Do not claim a tenant-capacity number without load tests. Include DB connection-pool and worker-concurrency limits.
